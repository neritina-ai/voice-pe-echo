# 設計說明

這份文件記錄本專案的技術決策：遇到的問題、考慮過的做法，以及最後選擇的理由。
使用方式請看 [使用手冊](user-guide.md)。

需求只有一句話：**PC 端程式執行後 24 小時收音，偵測 Voice PE 收到的聲音；我講一句話，就從電腦喇叭把原話放出來，直到我關閉程式。**
下面每一節對應一個為了做到這件事必須回答的問題。

---

## 1. 聲音要怎麼從 Voice PE 到電腦？

Voice PE 跑的是 ESPHome 韌體，透過 Wi-Fi 用 **ESPHome native API**（TCP 6053）和 Home Assistant 溝通。
平常的流程是：Voice PE 在本機偵測喚醒詞 →把麥克風串流給 Home Assistant →HA 做語音辨識，並在偵測到句子結束時通知 Voice PE 關麥克風。

考慮過的做法：

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 經過 Home Assistant 取得錄音 | 不動 Voice PE | HA 只把聲音交給語音辨識，沒有「把原始錄音即時交出來」的介面；要靠除錯錄音檔繞路，延遲高又脆弱。 |
| B. 自己寫韌體，直接把麥克風 UDP 串流給電腦 | 完全掌控 | 要編譯、刷韌體，門檻高；也失去官方韌體的更新、燈號與按鍵行為。 |
| **C. 電腦程式直接扮演「語音助理伺服器」** | **原廠韌體即可**；拿到的是 Voice PE 的 XMOS 晶片處理過（降噪、波束成形）的聲音 | 同一時間只能有一個語音助理伺服器，所以要先讓 HA 放開 Voice PE。 |

**選擇 C**。用 Home Assistant 官方維護的 Python 函式庫 [`aioesphomeapi`](https://github.com/esphome/aioesphomeapi) 連線（HA 本身也是用它），
訂閱語音助理（`subscribe_voice_assistant`，要求以 API 傳送音訊），在收到開始請求時回覆 port 0（＝「音訊直接走 API 連線」），
之後裝置就會每 32 ms 送來一段 16 kHz、16-bit、單聲道 PCM。新版韌體一次送兩個聲道：第 0 聲道是增強過的語音（HA 預設也用這個），第 1 聲道是原始聲音；本程式用第 0 聲道。

## 2. 怎麼做到「24 小時收音」，不用每句都喊喚醒詞？

查閱 Voice PE 韌體（[home-assistant-voice-pe](https://github.com/esphome/home-assistant-voice-pe) 的 `home-assistant-voice.yaml`）
與 ESPHome 的 `voice_assistant.cpp` 後，發現兩個關鍵行為：

1. **麥克風串流沒有逾時**。進入 `STREAMING_MICROPHONE` 狀態後，裝置會一直送聲音，直到伺服器送來 `STT_VAD_END`、`RUN_END` 或錯誤事件才停。
   平常是 HA 偵測到句子結束後送 `STT_VAD_END`；**本程式永遠不送**，所以一次開啟就能一直收音，斷句改在電腦上做。
2. **可以不用喚醒詞叫它開始**。伺服器送出帶 `start_conversation=True` 的公告（`VoiceAssistantAnnounceRequest`）時，
   裝置播完公告音後會自動開啟麥克風、向伺服器請求開始（HA 的 `assist_satellite.start_conversation` 就是用這個機制）。
   公告音使用韌體內建的喚醒提示音 `audio-file://wake_word_triggered_sound`，所以使用者會聽到「開始收音了」的提示，不需要電腦另外架 HTTP 伺服器。
   舊版韌體沒有這個內建檔案也沒關係：播放失敗時韌體有 2 秒的播放逾時，之後一樣會開始收音。

串流可能因為使用者按中央按鈕、說喚醒詞、靜音、斷線而停止，程式用一個「保持收音」的迴圈處理：

- 裝置停止串流 → 1.5 秒後重新請它開始。
- 靜音開關打開 → 程式主動結束這一輪（送 `RUN_END`，讓燈環正確顯示靜音的紅燈），等取消靜音再開始。
- 送出開始請求 15 秒內沒有收到聲音 → 提示可能原因並以遞增間隔（30 秒起、最多 5 分鐘）重試，避免一直播放提示音。
- 韌體太舊、沒有 `START_CONVERSATION` 功能 → 提示使用者說一次「Okay Nabu」或按中央按鈕；之後同樣一直收音。
- 斷線 → 2、4、8… 秒（最多 30 秒）後自動重連；若連線失敗，下一次改用主機名稱重新解析 IP（因應 DHCP 換 IP）。

結束程式時會先送 `RUN_END` 關麥克風、取消訂閱，再斷線，讓 Voice PE 回到正常狀態。

## 3. Home Assistant 同時連著怎麼辦？

ESPHome 的語音助理同一時間只接受一個訂閱者，第二個會被拒絕，而且**API 不會回錯誤給被拒絕的一方**，只會在裝置日誌寫一行
`Multiple API Clients attempting to connect to Voice Assistant`，並附上目前佔用者的名稱。

因此程式連線後也訂閱了裝置的警告等級日誌，看到這行就知道被誰佔用（例如 `Home Assistant 2026.10.1 (192.168.1.10)`），
明確告訴使用者去 HA 停用裝置，並每 30 秒重試訂閱；使用者停用 HA 之後會自動接手。
反過來，如果是本程式先佔用、HA 後來才想連，日誌裡的「目前佔用者」是本程式自己（`voice-pe-echo`），這時只提醒使用者「結束後要在 HA 重新載入」，不會誤判成自己被拒絕。

這個「停用 HA」的要求是 ESPHome 架構決定的，無法繞過；手冊因此把它寫成固定步驟，並說明用完如何復原。

## 4. 加密金鑰

Voice PE 韌體設定了 `api: encryption:`（不寫死金鑰）：加入 HA 時，HA 會產生隨機金鑰寫進裝置，並存在 HA 的
`.storage/esphome.encryption_keys`（以 MAC 位址為索引）與 `.storage/core.config_entries`（`noise_psk`）。HA 介面不會顯示它。

- 已加入 HA 的使用者：從上述檔案讀出金鑰（手冊提供 Terminal 附加元件的一行指令）。
- 不想找金鑰的使用者：恢復原廠設定後用 Improv（USB 或藍牙）設定 Wi-Fi，裝置沒有金鑰，可直接連線。

程式用 mDNS（`_esphomelib._tcp`）自動搜尋 Voice PE，TXT 紀錄會說明裝置是否已設定金鑰（`api_encryption` / `api_encryption_supported`），
所以在連線前就能提醒「需要金鑰」或「不需要金鑰」。金鑰錯誤、缺少金鑰屬於重試也無法解決的錯誤，程式會說明原因後結束。

## 5. 怎麼判斷「一句話」？

**語音偵測（VAD）**：使用 [Silero VAD](https://github.com/snakers4/silero-vad)（透過 [`pysilero-vad`](https://github.com/rhasspy/pysilero-vad)，Home Assistant Assist 也是用它）。
它是小型神經網路，對人聲判斷遠比「音量大小」準確，背景的冷氣、風扇聲不會誤觸發；每 32 ms 的音框只需約 0.2 ms 運算，24 小時執行也很輕。
它要求的 512 樣本視窗，正好等於 Voice PE 每次送來的大小。
`pysilero-vad` 沒有 Intel Mac 的預編譯版本，所以另外內建一個「音量高於自動學習的噪音底線 12 dB」的簡易偵測器作為備援（`--vad energy`）。

**斷句**（`segmenter.py`，純邏輯、可單元測試）：

| 參數 | 預設 | 作用 |
|---|---|---|
| 開始條件 | 最近 0.32 秒中有 0.19 秒是語音 | 單一雜音不會觸發。 |
| 前置緩衝 | 0.3 秒 | 保留偵測到開始之前的聲音，第一個字不會被切掉。 |
| 結束條件 | 連續 0.8 秒非語音 | 句中自然停頓不會被切斷。結束判斷用比開始低 0.15 的門檻（遲滯），避免輕聲的字被當成停頓。 |
| 保留尾巴 | 0.25 秒 | 播放起來不會太突然。 |
| 最短語音 | 0.3 秒 | 咳嗽、敲桌子會被略過。 |
| 最長一句 | 20 秒 | 一直有人聲（例如電視）時強制切段，避免永遠不播放。 |

用真實語音樣本驗證過：句內停頓（0.1～0.6 秒）不會切斷，句間停頓會正確分句。

## 6. 回授（最重要的問題）

**問題**：電腦喇叭播放的聲音被 Voice PE 收進去 → 被當成新的一句 → 再播放 → 無限循環。

Voice PE 的 XMOS 晶片有回音消除（AEC），但 AEC 需要「參考訊號」，它只拿得到 Voice PE **自己的**喇叭輸出，
對電腦喇叭的聲音完全無效。考慮過的做法：

| 做法 | 評估 |
|---|---|
| 只規定擺放距離 | 不可靠：距離無法讓迴音「消失」，只會變小；音量一大仍會循環。 |
| 在電腦端做 AEC（拿播放內容當參考訊號） | 需要精確對齊「播放」與「經網路回來的錄音」的時間，而 Wi-Fi 延遲會抖動；做不好反而殘留，複雜度與風險都高。 |
| 比對錄音與剛播放的內容是否相似再丟棄 | 啟發式判斷，有誤刪真話或漏網的可能。 |
| **半雙工閘門（採用）** | 播放時不收音，像對講機。簡單、確定、不依賴擺放；代價是播放中說的話不會被錄到，對「回聲」這個用途可以接受。 |

半雙工閘門的細節（`app.py`）：

1. 播放期間，丟棄所有收到的聲音。
2. 播放結束後再丟棄 `guard` 秒（預設 0.6 秒），涵蓋：房間殘響、音效卡緩衝、網路與裝置緩衝延遲。
   播放函式會等到「聲音實際離開喇叭」（取樣數 ÷ 取樣率，加上音效卡回報的輸出延遲）才算結束，藍牙喇叭的延遲也算在內。
3. 閘門打開時重設斷句器並進入 **ARMING** 狀態：必須先聽到 0.25 秒的安靜，才允許開始新的一句。
   即使有比預期更長的迴音尾巴跨過閘門，也因為「不是從安靜開始」而不會被當成一句話。

**驗證**：`tests/test_echo_with_fake_device.py` 模擬「喇叭聲音延遲 0.15 秒、加上 0.3 秒殘響、以 60% 音量回到麥克風」的房間，
確認兩句話只會各播放一次；同一個情境下的**對照組**（移除閘門）則確實發生無限回授——證明測試情境足以引發回授，而閘門擋住了它。

擺放建議（1 公尺以上、喇叭不正對、或戴耳機）仍寫在手冊裡，作為額外的保險，而不是唯一的防線。

## 7. 播放

- 使用 [`sounddevice`](https://python-sounddevice.readthedocs.io/)（PortAudio），Windows、macOS、Linux 都能用；Windows 與 macOS 的套件已內含 PortAudio。
- 優先以 16 kHz 直接播放；音效卡不支援時改用裝置預設取樣率，自行重新取樣。
- 預設把每句話的峰值調整到 -1 dBFS（最多放大 18 dB，避免把很小的聲音或雜音放得很大），前後加 10 ms 淡入淡出避免爆音。
- 可選擇另存 WAV（`--save-dir`），方便回頭聽 Voice PE 實際收到什麼。

## 8. 讓使用者「看得到」Voice PE 收到聲音

- 終端機最下方即時顯示狀態與音量列（dBFS，峰值保持），說話時會明顯跳動。
- Voice PE 燈環：開始收音時送 `STT_START`（慢速旋轉），偵測到說話送 `STT_VAD_START`（快速旋轉），句子結束後再送 `STT_START`。
  這兩個事件在韌體中只改變燈號，不會改變麥克風狀態，所以不會中斷串流。可用 `--no-led` 關閉。

## 9. 測試方式

沒有實體裝置也能完整測試：`tests/fake_voice_pe.py` 是一個依照 ESPHome 原始碼行為撰寫的**模擬 Voice PE**，
實作 ESPHome API 的明文協定，包含：只允許一個語音助理訂閱者並寫出拒絕日誌、公告後自動開始、以 API 串流麥克風、
按鈕停止、靜音開關、斷線，以及一個「聽得到電腦喇叭」的模擬房間。

```sh
pip install -e ".[test]"
pytest
```

| 測試 | 內容 |
|---|---|
| `test_segmenter.py` | 斷句：單句、句中停頓、分句、咳嗽略過、最長切段、ARMING。 |
| `test_audio.py` | 音量計算、正規化、淡入淡出、重新取樣、簡易 VAD。 |
| `test_cli.py` | 設定檔、環境變數、命令列的優先順序與錯誤檢查。 |
| `test_echo_with_fake_device.py` | 端對端：回聲與防回授（含對照組）、HA 佔用時等待與接手（新舊兩種日誌格式）、HA 晚到不影響、按鈕後自動恢復、靜音暫停、斷線重連。 |

也可以手動跑模擬裝置，用真正的命令列程式連上去看畫面：

```sh
python tests/fake_voice_pe.py 16053          # 視窗 1：模擬 Voice PE，每 6 秒「說」一句話
python -m voice_pe_echo --host 127.0.0.1 --port 16053 --vad energy   # 視窗 2
```

（模擬的「說話」是合成音，Silero 不會把它當人聲，所以手動測試時用 `--vad energy`。）

## 10. 已知限制

- **半雙工**：電腦播放期間與之後 0.6 秒內說的話不會被錄到。
- 使用本程式時 Home Assistant 不能同時使用這台 Voice PE 的語音助理（ESPHome 架構限制）。
- 開發時沒有實體 Voice PE，硬體互動是依照 Voice PE 韌體與 ESPHome 原始碼的行為實作，並以模擬裝置驗證；
  若實機出現與文件不符的狀況，請用 `-vv` 執行並保留訊息，方便對照裝置日誌調整。
